# PetClinic REST API — автотесты на Go

API-тесты для [Spring PetClinic REST](https://github.com/spring-petclinic/spring-petclinic-rest):
владельцы, поиск, питомцы и негативные проверки. Требуется Go 1.22+.

## Запуск

Поднять тестируемый сервис:

```bash
docker run --rm -p 9966:9966 springcommunity/spring-petclinic-rest

```

Сервис готов, когда отвечает `http://localhost:9966/petclinic/api/pettypes`. Авторизация не нужна.

Поставить зависимости и прогнать всё:

```bash
go mod download
go test ./tests -count=1 -v

```

Отдельные группы:

```bash
make test-owners    # CRUD владельца, список и поиск
make test-pets      # питомцы и их связь с владельцем
make test-negative  # несуществующие объекты и невалидные тела
```

Под капотом это фильтр по имени теста, так что можно и напрямую:

```bash
go test ./tests -run 'TestOwnersCRUD/TestOwnerLifecycle' -count=1 -v
```

## Адрес сервиса

Переопределяется переменными окружения:

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `PETCLINIC_BASE_URL` | базовый URL API | `http://localhost:9966/petclinic/api` |
| `PETCLINIC_TIMEOUT` | таймаут HTTP-клиента | `10s` |

```bash
PETCLINIC_BASE_URL=http://stand:9966/petclinic/api go test ./tests -count=1
make test BASE_URL=http://stand:9966/petclinic/api
```

## Структура

```
config/            базовый URL и таймаут из окружения
internal/
  models/          типизированные запросы и ответы (Owner, Pet, ProblemDetail)
  client/          HTTP-клиент: типизированный результат + сырой ответ
  checkers/        переиспользуемые проверки статусов, полей и ошибок валидации
  fixtures/        генерация валидных данных и уборка созданного
tests/             сценарии, по файлу на группу проверок
```

Клиент возвращает и модель, и сырой `Response` — на `204` и `404` тела нет, проверять
можно только по статусу.

## Что проверяется

Объём держится в рамках четырёх групп из задания — 10 тестов, 21 проверка. Остальные ручки
сервиса (визиты, ветеринары, специальности, пользователи) в объект тестирования не входят.

- **`owners_crud_test.go`** — жизненный цикл владельца: создание, чтение по id, обновление,
  удаление и состояние после удаления (404 с пустым телом).
- **`owners_list_test.go`** — поиск по фамилии находит ровно созданного владельца, он же
  присутствует в общем списке; отдельно зафиксирована семантика фильтра — префикс,
  регистрозависимость и 404 вместо пустого массива.
- **`pets_test.go`** — питомец добавляется существующему владельцу: сверяются имя, дата
  рождения, тип и связь через `ownerId`, в том числе со стороны `owner.pets[]`.
- **`negative_test.go`** — запросы к несуществующим объектам и некорректные тела с разбором
  по конкретным полям, включая неизвестный тип питомца и синтаксически битый JSON.

## Факты о формате запроса

Выяснены до написания тестов. Это не проверки корректности, а условия, без которых валидный
запрос не собрать — реализация здесь совпадает со спецификацией.

- Тип питомца передаётся **вложенным объектом** `type: {id, name}` — в схеме `PetFields` поле
  `type` объявлено как `$ref: PetType` и обязательно. Плоский `typeId` отклоняется с 400.
- `birthDate` — строка `yyyy-MM-dd`.
- `telephone` — только цифры и ровно 10 знаков; иная длина отваливается на уровне БД с 500.
- `firstName` / `lastName` — только буквы, 1–30 символов.
- Питомцы приходят вложенными в `Owner.pets[]`, отдельной ручки за списком питомцев владельца нет.

## Расхождения реализации со спецификацией

Сверено с `openapi.yml` из репозитория сервиса. В пяти местах реализация нарушает собственную
спецификацию. **Ожидания в тестах выставлены по фактическому поведению** — этого прямо требует
задание («ожидания должны соответствовать фактическому API-контракту»), и тесты, ассертящие
спецификацию, были бы постоянно красными. Каждое расхождение ниже — кандидат в баг-репорт.

| Ручка | Спецификация | Реализация | Где закреплено |
|---|---|---|---|
| `GET /owners?lastName=` | объявлены только `200` / `304` / `500`; `404` нет в контракте вовсе | `404` с пустым телом на пустую выдачу | `TestSearchSemantics` |
| `GET /owners/{id}` | `404` **с телом** `ProblemDetail` | `404` с пустым телом | `TestMissingEntities` |
| `PUT /owners/{id}` | `200` + `Owner`, «Update successful» | `204` без тела | `TestOwnerLifecycle` |
| `DELETE /owners/{id}` | `200` + `Owner` | `204` без тела | `TestOwnerLifecycle` |
| `POST /owners` | `400` + `ProblemDetail` на некорректный запрос | `500` на синтаксически битый JSON | `TestMalformedBody` |

Практические следствия для кода тестов:

- результат `PUT` сверяется следующим `GET` — в ответе самого `PUT` тела нет;
- на `404` тело не парсится, проверяется только статус и его пустота;
- поиск без совпадений ожидается как `404`, а не как `200 []`;
- разбирать `ProblemDetail` имеет смысл на `400` и на `404` от несуществующего типа питомца —
  это единственный `404` в сервисе, приходящий с телом.

Дополнительно замечено, но за рамками четырёх групп задания: запрос без `Content-Type`, нечисловой
`id` в пути и неподдерживаемый метод тоже дают `500` вместо `4xx`.

## Данные и независимость тестов

Каждый тест создаёт всё, что ему нужно, и не опирается на сидовые записи. Фамилия владельца
генерируется уникальной, поэтому поиск находит только свою запись и параллельные прогоны не мешают
друг другу.

Уборка идёт в `TearDownSuite`, то есть отрабатывает и после падения теста. **Питомцы удаляются
раньше владельцев**: удаление владельца каскадом уносит не только его питомцев, но и их тип из
справочника `/pettypes` — если удалять владельца первым, общий справочник деградирует от прогона
к прогону и тесты начинают флакать. `404` при уборке считается нормой: объект мог быть удалён самим
сценарием.
